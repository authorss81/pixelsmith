# pixelsmith

A local-first image resizer. Rust engine, Flutter front end, Windows + Android +
iOS + macOS + Linux.

**It never uploads anything, because it has no network capability to upload
with.** That is a structural property, not a policy setting — see
[Security](#security) for how to verify it yourself.

---

## Status

This repository is under active automated construction. An autonomous
[opencode](https://opencode.ai) pipeline reads the phase prompts in
`workspace/`, implements one phase per run, reviews its own work, verifies it,
and then writes the next set of phases from a self-audit.

## What the engine does today

- Decode JPEG, PNG, WebP, GIF, TIFF, BMP, ICO, and HEIC/HEIF behind the `heic`
  feature.
- Encode JPEG, PNG, WebP, GIF, TIFF, BMP, ICO — plus AVIF, and **lossy WebP
  through libwebp** in the default build, so a byte ceiling and a quality slider
  both work for WebP.
- Resize with five resampling kernels, five fit modes, one resampling pass.
- **Target-size mode**: give it a byte ceiling and it binary-searches quality to
  land just under it, returning the highest quality that fits. Converges in about
  seven encodes. This is the feature every competitor does badly.
- Read EXIF, and **strip it by re-encoding** rather than by clearing tags, so
  maker notes and embedded thumbnails cannot survive. GPS is never written back.
- **Colour management**: sRGB and Display-P3, with the ICC profile read out of
  JPEG, PNG and WebP and the pixels converted before any geometry runs.
- **Animated GIF, honestly**: an animation exported as a GIF keeps every frame
  and its delay; exported as anything else it is refused in a sentence naming the
  frame count, rather than flattened without saying so.
- Progressive JPEG and chroma subsampling, defaulting by content — 4:2:0 for
  photographs, 4:4:4 for screenshots.
- Reject decompression bombs from the header, before allocating a pixel buffer.
- Run batches in parallel with deterministic output, deduplicate by content hash,
  account for every file by success / skip / failure, and cancel without leaving
  half-written files.
- Never trust a filename. Format comes from magic bytes; output names are
  sanitised against path traversal.

Not yet: AVIF **decode** (this build can write an AVIF and cannot read one back,
and `capabilities()` says so), and any user interface at all.

## Getting it

Downloads are on the [releases page](https://github.com/authorss81/pixelsmith/releases).

| Platform | File | What to expect |
| --- | --- | --- |
| **Windows** | `pixelsmith-<version>-windows-x64.zip` | Unzip anywhere and run `shrinkray.exe`. No installer, no admin rights, no registry. |
| **Android** | `pixelsmith-<version>-android.apk` | Sideload it. Installs with USB debugging on. The `.aab` in the same release is what Google Play takes. |

Every release attaches a `SHA256SUMS.txt` and a CycloneDX SBOM. Compare with
`sha256sum -c SHA256SUMS.txt` before you trust a download.

**Windows SmartScreen will warn you.** The EXE is not code-signed, because a
signing certificate is issued to an organisation and paid for by one and this
project has neither. SmartScreen shows "unrecognised app", and on some builds
refuses to run it until you click *More info → Run anyway*. That is what Windows
does with every unsigned binary, not something specific to this one. An MSI or an
MSIX would be signed too — or would ask for admin rights — so the portable ZIP is
the honest shape for an unsigned project. If you would rather not click through
a warning about a program you have not read, [build it](#building-it-yourself);
it is four commands.

**Read [CHANGELOG.md](CHANGELOG.md) before you install.** Its second half is
"what a user cannot yet do", and the short version is that the user interface is
still a shell: the app opens and reports the engine's version. The engine resizes
images and the engine is tested; no screen calls it yet.

## Building it yourself

```bash
# The engine, standalone
cd core
cargo test                                     # the default features: avif + webp-lossy
cargo clippy --all-targets --all-features -- -D warnings
cargo build --release
```

**The feature flags are the build, so they are spelled out rather than implied.**
`default = ["avif", "webp-lossy"]`; `streaming`, `simd` and `heic` are off, and
each one changes what the crate can do. Every combination below compiles and its
tests run, and the gate checks nine of them on every push:

```bash
cd core
cargo test --no-default-features                 # no optional codec: the AVIF and
                                                  # lossy-WebP refusal arms
cargo test --features streaming                  # the low-peak-memory decode path
cargo test --features simd                       # the fast_image_resize kernel
cargo test --all-features                        # everything, which is what CI runs

cd .. && bash scripts/feature-matrix.sh          # all nine, in about a minute
bash scripts/verify.sh                           # the gate: fmt, clippy, tests,
                                                 # matrix, release build, rustdoc,
                                                 # the Flutter side, the FFI contract
```

The two opt-in paths are named in [`docs/BENCHMARKS.md`](docs/BENCHMARKS.md) and
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md): `streaming` trades a second decode
path for 4 MB instead of 613 MB on a 120-megapixel source, and `simd` is 2.8× to
19.9× on an x86-64 runner with AVX2 — 2.8× to 12.5× on a second one, same lockfile,
so the number belongs to the CPU — and unmeasured on the ARM phone this ships to.
Neither is on by default, and neither is turned on by the flag list above — you
asked for them.

The app is a submodule, so it comes with a clone of this repository:

```bash
git submodule update --init --recursive
( cd app && flutter pub get && flutter analyze && flutter test )

# Android: the engine has to be cross-compiled for every ABI Flutter packages.
rustup target add aarch64-linux-android armv7-linux-androideabi x86_64-linux-android
cargo install cargo-ndk
( cd core && cargo ndk -t arm64-v8a -t armeabi-v7a -t x86_64 \
    -o ../app/android/app/src/main/jniLibs build --release --lib )
( cd app && flutter build apk --release )

# Windows, on a Windows machine — flutter build windows does not cross-compile.
( cd core && cargo build --release --lib )
cp core/target/release/pixelsmith_core.dll app/windows/runner/
( cd app && flutter build windows --release )
```

Then open what you built, rather than trusting the log:

```bash
bash scripts/verify-release-artifact.sh apk \
  app/build/app/outputs/flutter-apk/app-release.apk \
  --abi-source app/android/app/src/main/jniLibs
bash scripts/verify-release-artifact.sh windows app/build/windows/x64/runner/Release
```

An APK with no native library installs, opens, and throws on the first resize.
That is why the check exists. The full release runbook — signing, the secrets,
the checksum table and the draft release — is [docs/RELEASE.md](docs/RELEASE.md).

## Security

The engine's dependency tree contains no HTTP, TLS, socket or DNS crate. This is
checked mechanically on every verification run, not asserted in a README:

```bash
cargo tree --manifest-path core/Cargo.toml | grep -E 'reqwest|hyper|tokio|std::net'
# no output
```

Two more properties worth stating plainly:

- **Memory-safe parsing.** Rust, so the usual class of parser bugs does not
  apply. This matters more than usual here: image decoders are the attack surface
  of an app whose entire job is opening files you did not create.
- **Bounded by default.** Dimensions and pixel counts are checked against
  `validate::Limits` before any buffer is allocated, so a file claiming
  60000×60000 is rejected on sight rather than costing 14 GB.

**To report a vulnerability, see [SECURITY.md](SECURITY.md).** The full policy —
threat model, what "secure" means here, the fuzzing setup, disclosure route and
supported versions — is in **[docs/SECURITY.md](docs/SECURITY.md)**, and the
supply chain behind it (licence and advisory policy, the SBOM, release hashes, and
**which targets build reproducibly and which are not measured**) is in
**[docs/SUPPLY-CHAIN.md](docs/SUPPLY-CHAIN.md)**.

To check the no-network claim yourself, against the release artefact rather than
against this repository's word for it:

```bash
bash scripts/no-network-report.sh --build
```

That checks the dependency graph, the source, the release library's dynamic
imports *and* its undefined dynamic symbols — the last of which is the strongest,
because `ldd` cannot see a statically linked `socket()` call. The check that
actually settles it is not a script: install the app, disconnect from the network,
and use it. It should not notice.

`fuzz/` runs `cargo-fuzz` over every decode path, and `scripts/fuzz.sh` is the
wrapper.

## The pipeline

```
schedule / self-retrigger
        │
        ▼
  select-phase ──── reads workspace/ markers via the GitHub API, no checkout.
        │           Picks: unverified work → deferred → lowest not-done.
        ▼
   run-phase ───── opencode run on workspace/<phase>/PROMPT.md
        │           Model chain: space-bunny-free, then fallbacks.
        │           Evidence gate: no file changes ⇒ not attempted.
        │           Checkpoints partial work to px-wip/<phase> every 5 min.
        ▼
    verify ──────── scripts/verify.sh. Only this job may write .done.
        │
        ▼
    review ──────── reviewer subagent, read-only, emits numbered findings.
        │            A build agent applies the fixes.
        ▼
   retrigger ───── POSTs px_tick to itself; the next run starts in ~15s.
```

When every phase is done, an **audit** job runs once: the auditor reads the tree,
writes `docs/AUDIT.md`, and generates the next phases. Because it pushes new
`workspace/phase-NN/` directories, the selector picks them up on the next tick.
That is the loop closing, and it needs no change to the workflow.

**Limits.** 250 runs, 80 phases, 3 attempts per phase, 5 rate-limit deferrals per
phase, 3 verification failures, 2 no-work failures. A phase that exhausts any of
them becomes `.blocked` and is skipped. There is no path by which this loop runs
forever on its own.

**Recovery.** Transient failures recover themselves: rate limits retry on the
next tick, a killed job resumes from a checkpoint branch every 5 minutes, and a
rejected push is recovered from `px-recovery/<phase>`. The log tail is written to
the job's step summary as well as to an artifact, so a failed upload does not
destroy the diagnosis. Every marker, every limit, and every manual recovery
command is in **[docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)**.

### Running it yourself

1. Create a public repository.
2. Copy `scripts/`, `workspace/`, `opencode.json`, `.opencode/agent/` and
   `.github/workflows/automation.yml` into it.
3. Settings → Secrets and variables → Actions → add `OPENCODE_API_KEY`.
4. Actions → automation → Run workflow.

## Configuration

`opencode.json` sets the model and the hard permissions. `webfetch` and
`websearch` are **denied**, so no phase can introduce a network call even by
accident. To change the model chain, edit `OPENCODE_MODEL` in the workflow; the
runner walks the list one entry at a time via `--model`.
