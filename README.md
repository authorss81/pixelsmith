# pixelsmith

A local-first image resizer. Rust engine, Flutter front end, Windows + Android +
iOS + macOS + Linux.

**It never uploads anything, because it has no network capability to upload
with.** That is a structural property, not a policy setting — see
[Security](#security) for how to verify it yourself.

## What the engine does today

- Decode JPEG, PNG, WebP, GIF, TIFF, BMP, ICO.
- Encode JPEG, PNG, WebP, GIF, TIFF, BMP, ICO — plus AVIF, and **lossy WebP
  through libwebp** in the default build, so a byte ceiling and a quality slider
  both work for WebP.
- Resize with five resampling kernels, five fit modes, one resampling pass.
- **Target-size mode**: give it a byte ceiling and it binary-searches quality to
  land just under it, returning the highest quality that fits. Converges in about
  seven encodes. This is the feature every competitor does badly.
- Read EXIF, and **strip it by re-encoding** rather than by clearing tags, so
  maker notes and embedded thumbnails cannot survive.
- Reject decompression bombs from the header, before allocating a pixel buffer.
- Run batches in parallel with deterministic output, and cancel without leaving
  half-written files.
- Never trust a filename. Format comes from magic bytes; output names are
  sanitised against path traversal.

Not yet: HEIC decode, colour management, animation preservation, AVIF decode.
Each has a phase.

## Security

The engine's dependency tree contains no HTTP, TLS, socket or DNS crate. This is
checked mechanically on every verification run, not asserted in a README:

```bash
cargo tree --manifest-path core/Cargo.toml | grep -E 'reqwest|hyper|tokio|std::net'
# no output
```

Two more properties worth stating plainly:

- **Memory-safe parsing.** Rust, so the usual class of parser bugs does not
  apply. This matters more than usual here: image decoders are the attack surface
  of an app whose entire job is opening files you did not create.
- **Bounded by default.** Dimensions and pixel counts are checked against
  `validate::Limits` before any buffer is allocated, so a file claiming
  60000×60000 is rejected on sight rather than costing 14 GB.

The fuzz harness lands in phase-02. Supply-chain policy, an SBOM and reproducible
builds land in phase-15.

## The pipeline

```
schedule / self-retrigger
        │
        ▼
  select-phase ──── reads workspace/ markers via the GitHub API, no checkout.
        │           Picks: unverified work → deferred → lowest not-done.
        ▼
   run-phase ───── opencode run on workspace/<phase>/PROMPT.md
        │           Model chain: space-bunny-free, then fallbacks.
        │           Evidence gate: no file changes ⇒ not attempted.
        │           Checkpoints partial work to px-wip/<phase> every 5 min.
        ▼
    verify ──────── scripts/verify.sh. Only this job may write .done.
        │
        ▼
    review ──────── reviewer subagent, read-only, emits numbered findings.
        │            A build agent applies the fixes.
        ▼
   retrigger ───── POSTs px_tick to itself; the next run starts in ~15s.
```

When every phase is done, an **audit** job runs once: the auditor reads the tree,
writes `docs/AUDIT.md`, and generates the next phases. Because it pushes new
`workspace/phase-NN/` directories, the selector picks them up on the next tick.
That is the loop closing, and it needs no change to the workflow.

**Limits.** 250 runs, 80 phases, 3 attempts per phase, 5 rate-limit deferrals per
phase, 3 verification failures, 2 no-work failures. A phase that exhausts any of
them becomes `.blocked` and is skipped. There is no path by which this loop runs
forever on its own.

**Recovery.** Transient failures recover themselves: rate limits retry on the
next tick, a killed job resumes from a checkpoint branch every 5 minutes, and a
rejected push is recovered from `px-recovery/<phase>`. The log tail is written to
the job's step summary as well as to an artifact, so a failed upload does not
destroy the diagnosis. Every marker, every limit, and every manual recovery
command is in **[docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)**.

### Running it yourself

1. Create a public repository.
2. Copy `scripts/`, `workspace/`, `opencode.json`, `.opencode/agent/` and
   `.github/workflows/automation.yml` into it.
3. Settings → Secrets and variables → Actions → add `OPENCODE_API_KEY`.
4. Actions → automation → Run workflow.

## Configuration

`opencode.json` sets the model and the hard permissions. `webfetch` and
`websearch` are **denied**, so no phase can introduce a network call even by
accident. To change the model chain, edit `OPENCODE_MODEL` in the workflow; the
runner walks the list one entry at a time via `--model`.
